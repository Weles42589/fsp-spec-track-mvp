# ФСП «спец. трек» — платформа-агрегатор ИТ-вакансий

MVP веб-платформы для хакатона ФСП: **работодатель находит кандидата и направляет
приглашение**, а не кандидат рассылает отклики. Доступ к банку профилей определяется
уровнем организации процессов в компании, профиль кандидата подтверждается объективно —
сертификатом КИТ i.moscow, историей ФСП и барометром амбиций.

**Статус:** демонстрационная сборка MVP (черновик документации v0.9, октябрь 2026).
Полное описание — [`docs/FSP-documentation.pdf`](docs/FSP-documentation.pdf)
(источник: [`docs/documentation.html`](docs/documentation.html)).


## ⚠️ Важно: сейчас видны все внутренние логики и административные процессы

Приложение намеренно работает в режиме **полной демонстрационной прозрачности** —
чтобы жюри и заказчик видели: ранжирование детерминированно, объяснимо и соответствует
ТЗ, а не является «чёрным ящиком».

**В продуктивной версии кандидат и работодатель этого видеть не будут.** Что открыто
сейчас:

| Видно сейчас | Где | В продукте |
|---|---|---|
| **Как начисляются баллы релевантности**: веса 35 / 25 / 20 / 10 / 10 и поштучные причины, включая штраф за неверифицированный грейд и бонус за амбициозность | `/employer/vacancies/{id}`, карточка соответствия (`_partial_match.html`, `MATCH_WEIGHTS`) | Только процент и 2–3 человеческие причины, без весов и арифметики — это коммерческая тайна и защита от «заточки» анкет под алгоритм |
| **Как начисляются баллы ФСП**: сумма баллов за достижения, пороги категорий 150 / 100 / 60 / 30 → S/A/B/C/D | `/candidate`, шаг 2 регистрации | Баллы и категория приходят из реестра ФСП; методика начисления принадлежит оператору ФСП и не публикуется |
| **Почему профиль закрыт**: «профиль заполнен не полностью», «кандидат скрыл профиль», «уровень профиля выше, чем доступен при текущем уровне организации процессов» + замаскированные имена недоступных кандидатов | `/employer/bank`, `/employer/vacancies/{id}`, `employer_candidate_restricted.html` | Нейтральное «Профиль недоступен» и агрегированный счётчик: текущая формулировка фактически раскрывает тир работодателя и несёт юридические риски |
| **Уровень процессов (тир) работодателя** словами и расшифровкой, а также полная матрица видимости | `/employer`, `/employer/bank`, `/register/employer/survey`, лендинг `/` | По ТЗ 5.2 работодатель **не видит свой тир** ни цифрой, ни словами; кандидату — только словесный уровень конкретной компании в приглашении |
| **Какие поля закрыты** для работодателя (`TIER_FIELDS`) | банк и страница потребности | Показываются только реально открытые поля, без перечня скрытых |
| **Рейтинг компании**: сырые сигналы (тендеры, реестр отечественного ПО, отзывы, разрыв зарплат) и коэффициенты формулы | карточка потребности, `/needs/{id}` | Сигналы парсятся из внешних источников, методика закрыта — иначе накрутка отзывов и претензии компаний |
| **Словарь модерации** («красные флаги», 13 формулировок) и замечания к профилю | `/needs/{id}`, кабинет кандидата | Только факт проверки и конкретное действие для пользователя |
| **Код подтверждения email прямо на экране**, сноска «вместо SMTP используется заглушка» | `/verify` (`demo_code`) | Код уходит по почте / через ФСП ID (Keycloak); показ кода = обход аутентификации |
| **Демо-учётные записи и мок-реестр ФСП** (8 адресов `*@fsp.demo`), демо-компании, демо-сертификат КИТ, сырой текст распознавания `kit_raw` | `/login`, `/register/candidate/fsp`, шаг 3 регистрации | Реестр ФСП и проверка сертификата у провайдера; подсказки демо-логинов удалены |
| **Открытый Swagger `/api/docs`**, `/health`, файл `database.db` рядом с кодом, путь к БД через `DATABASE_URL` | `main.py`, корень репозитория | Документация API закрыта или во внутренней сети; БД — на защищённом томе, в репозитории её нет |
| **Административные процессы как таковые**: нет ролей администратора и модератора, нет журнала аудита, таблицы создаются `create_all`, данные правятся вручную в SQLite | `database.py`, `fsp_mock.py` | Админ-панель, аудит-лог, миграции (Alembic), бэкапы, разделение окружений |
| **Нет продуктивных средств защиты**: rate limit и капчи на `/login` и `/verify`, лимитов приглашений, модерации текстов, уведомлений, хранения текста согласия 152-ФЗ, удаления профиля | — | Обязательны до релиза: перебор 6-значного кода, спам-приглашения, требования 152-ФЗ |

## Стек

Python 3.13 · FastAPI · SQLModel (SQLAlchemy + Pydantic) · SQLite · Jinja2 ·
Pico CSS · pdfplumber. Без ML, эмбеддингов, векторных БД, Redis/Celery и внешних
сервисов — вся логика детерминированная, на правилах, и запускается на обычном
ноутбуке.

## Быстрый старт

```bash
# 1. Зависимости
python3.13 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 2. Запуск: таблицы создаются при старте, пустая база заполняется демо-стендом
uvicorn main:app --reload
#    → http://127.0.0.1:8000     (Swagger в демо-сборке: /api/docs)

# 3. Проверка готовности
curl http://127.0.0.1:8000/health

# 4. Тесты (95 проверок, работают на временной копии БД)
python3.13 -m pytest
```

Демо-вход: любой корректный email и роль; **код подтверждения показывается на странице
`/verify`** (SMTP не подключён). История ФСП подтягивается для адресов из мок-реестра
`fsp_mock.FSP_REGISTRY` (`artem.petrov@fsp.demo`, `anna.sokolova@fsp.demo`,
`mark.ivanov@fsp.demo`, `olga.smirnova@fsp.demo`, `sergey.orlov@fsp.demo`,
`maria.lebedeva@fsp.demo`, `nikita.zaitsev@fsp.demo`, `sofia.morozova@fsp.demo`);
любой другой email — сценарий «истории ФСП нет» (0 баллов, категория D).
Сертификат КИТ для демо — текст `kit_parser.DEMO_CERTIFICATE_TEXT`, сохраните его в
`kit.txt` и загрузите на шаге 3 регистрации или в кабинете. Учётные записи демо-стенда
перечислены прямо на `/login` — список берётся из `seed.demo_accounts()`, поэтому
подсказка не расходится с содержимым базы.

Потребности стенда: «Backend Middle» и «DS Middle» у тира 3, «Frontend Junior» у тира 2,

в статусе `accepted` (контакты раскрыты) и одно `sent` (имя кандидата замаскировано).

Данные создаются штатными сервисами (`apply_candidate_profile`, `connect_fsp`,
`parse_kit_upload`, `apply_kit`, `apply_employer_profile`, `apply_employer_survey`),
поэтому грейд, специализация, амбициозность, категория ФСП и тир рассчитываются
правилами приложения, а не записываются вручную.

```bash
python3.13 seed.py            # пустая база → демо-набор и отчёт о стенде
python3.13 seed.py --force    # очистить базу и пересобрать стенд заново
DATABASE_URL="sqlite:///demo.db" python3.13 seed.py --force   # стенд в отдельном файле БД
```

Отчёт печатает состав стенда и матрицу видимости (тир 3 → 6 анкет, тир 2 → 5, тир 1 → 2) —
его удобно показать жюри; те же цифры проверяет `tests/test_seed.py`.

`database.db` в репозитории уже заполнен этим стендом: 6 кандидатов, 3 работодателя,
4 потребности, 2 приглашения, откликов и сессий нет — можно сразу запускать
`uvicorn main:app --reload` и показывать защиту.

## Как считается подборка (кратко)

> Это внутренняя методика: в демо она показана в интерфейсе, в продукте закрывается
> (см. раздел «⚠️ Важно» выше).


| Правило | Формула |
|---|---|
| Специализация | КИТ-сертификат → дисциплина ФСП → стек → ручной выбор (ручной выбор не перезаписывается) |
| Грейд | `kit_grade` → буква J/M/S в номере сертификата → ручной грейд → барометр (≥2 флагов → middle) → junior. Только КИТ даёт `is_verified` |
| Амбициозность | Флаги: капитан/архитектор в команде, «обсуждаем и влияю», широкий стек (≥3), капитан/архитектор в ФСП. Вердикт при ≥2 флагов |
| Тир работодателя | Число «здоровых» ответов из 6: ≥5 → 3 «развитые процессы», 3–4 → 2 «базовые», 0–2 → 1 «начальные» |
| Матрица видимости | Топ ФСП (senior + S/A либо капитан с баллами) → виден только тиру 3; middle/senior и амбициозные новички → тиру 2; новички без амбиций → всем |
| Поля карточки | Тир 1: специализация, грейд, верификация, баллы КИТ, стек, достижения кратко; тир 2: + амбициозность и роль ФСП; тир 3: + город и полный профиль |
| Релевантность | 35 специализация + 25 стек + 20 грейд + 10 верификация + 10 история ФСП, отсечение до 0…100; при равенстве — порядок ТЗ 6.6 (верификация → баллы КИТ → баллы ФСП → роль ФСП → амбиции) |
| Баллы ФСП | Сумма баллов достижений; категория: ≥150 S, ≥100 A, ≥60 B, ≥30 C, иначе D |
| Рейтинг компании | 3.0 + (отзывы − 3) × 1.5 + 1.0 за реестр отечественного ПО + тендеры (до 1.5) − (разрыв зарплат − 5) × 0.6 + (тир − 2) × 0.8; метки: ≥7.5 высокий, ≥5.0 средний |
| Контакты | ФИО и email раскрываются работодателю только при статусе приглашения `accepted`; до этого — маскированное имя |

## Маршруты

48 HTTP-операций, все страницы серверные. Публичные: `/`, `/health`, `/login`,
`/verify`, `/logout`, `/register/*`. Кандидат: `/candidate`, `/candidate/edit`,
`/candidate/visibility`, `/candidate/fsp/*`, `/candidate/kit`, `/needs`,
`/needs/{id}`, `/needs/{id}/apply`, `/candidate/applications`,
`/candidate/invitations[/{id}][/accept|/reject]`. Работодатель: `/employer`,
`/employer/survey`, `/employer/vacancies/new`, `/employer/vacancies/{id}`
(`[/toggle|/delete|/invite]`), `/employer/bank`, `/employer/candidates/{id}`,
`/employer/applications[/{id}/status]`, `/employer/invitations[/{id}/status]`.
Полная таблица — глава 8 документации.

```bash
python3.13 -m compileall -q .                        # модули
python3.13 -m pytest                                 # весь смоук-набор (testpaths в pytest.ini)
python3.13 -m pytest tests/test_smoke_strict.py -v   # только строгий рендер страниц
python3.13 -m pytest -k employer                     # только сценарий работодателя
```

Смоук-сценарии перенесены в репозиторий. `tests/conftest.py` до импорта приложения
выставляет `DATABASE_URL` на временный файл, создаёт таблицы и сид-данные (кандидаты из
мок-реестра ФСП — один с КИТ, один скрыт из банка; работодатели тиров 3 и 1;
потребности, отклик, приглашение), поэтому `database.db` из репозитория тесты не
изменяют. `TestClient` создаётся с `follow_redirects=False`, чтобы guard-функции были
видны как код 303, а не как «успешный» переход. После любых правок шаблонов, маршрутов
или правил в `logic.py` набор нужно прогонять заново.

## Что нужно закрыть до продуктивного релиза (P0)

1. Убрать показ кода подтверждения, подключить SMTP или ФСП ID / Keycloak.
2. Скрыть тир от работодателя (ТЗ 5.2) — во всех шаблонах кабинета и анкеты.
3. Заменить причины закрытия профиля нейтральными, убрать замаскированные имена
   недоступных кандидатов.
4. Убрать веса и арифметику релевантности из интерфейса (глобал `MATCH_WEIGHTS` в
   `web.py`, `vacancy_detail.html`, `_partial_match.html`).
5. Закрыть Swagger `/api/docs`, `/health`, демо-учётки и подсказки логинов; убрать
   `database.db` из репозитория.
