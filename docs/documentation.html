Стек: Python 3.13 · FastAPI · SQLModel · SQLite · Jinja2 · Pico CSS · pdfplumber

Статус: MVP для демонстрации на хакатоне ФСП. Документ — черновик; источник требований — TZ.txt и «ФСП спец. трек ТЗ.pdf» в корне репозитория.

1. Назначение платформы и ключевая механика

Платформа ФСП «спец. трек» связывает амбициозных ИТ-специалистов — участников и выпускников ФСП, держателей сертификатов КИТ i.moscow — и организации с высоким уровнем организации инженерных процессов.

Инверсия привычной механики job-сайта: не кандидат рассылает отклики, а работодатель находит кандидата в банке профилей и направляет приглашение с вилкой зарплаты. Кандидат получает входящие предложения и сам решает, принимать или отклонить. Дополнительно реализован встречный поток: кандидат видит «банк потребностей» (открытые вакансии) и может откликнуться сам.

1.1. Три источника достоверности профиля

  • Сертификат КИТ i.moscow — центр оценки компетенций: грейд, баллы (0–100), специальность, номер и дата сертификата. Загружается PDF или текстовая копия, разбирается регулярными выражениями (глава 6). Грейд из сертификата имеет высший приоритет и даёт метку «верифицирован».
  • История ФСП — достижения участника (дисциплина, соревнование, место, роль, баллы). В MVP берётся из мок-реестра fsp_mock.py по email; в продукте — из реестра ФСП. Даёт сумму баллов и категорию S–D.
  • Барометр амбиций — три вопроса анкеты кандидата, из которых выводятся четыре флага; два и более флага дают вердикт «амбициозный профиль».

1.2. Ключевая идея разграничения доступа

Работодатель видит не всех кандидатов, а только тех, чей уровень профиля соответствует его «тиру» — оценке того, как компания относится к сотрудникам и как устроены её инженерные процессы. Тир считается из шести нейтральных вопросов анкеты (раздел 6.4 ТЗ) и определяет: (а) какие профили доступны в банке, (б) какой состав полей карточки открыт. ФИО и контакты кандидата раскрываются работодателю только после того, как кандидат принял приглашение.

1.3. Принципы реализации

  • Детерминированность. Никаких ML-моделей, эмбеддингов, векторных БД и внешних сервисов: словари, регулярные выражения, сравнения, сортировки. Каждый признак объясняется текстом.
  • Лёгкость. Запуск на обычном ноутбуке без GPU; SQLite + FastAPI + шаблоны; отклик мгновенный (сотни записей).
  • Без брокеров и воркеров. Нет Redis, RabbitMQ, Celery, фоновых задач и сложных миграций.
  • Производные значения не хранятся. Грейд, амбициозность, категория ФСП, релевантность считаются на лету из правил — не разъезжаются при изменении исходных данных.

3.3. Соглашения кода

  • Каждая функция помечена номером раздела ТЗ в docstring — соответствие требованиям проверяется построчно.
  • Все страницы рендерятся на сервере (Jinja2); формы отправляются POST и завершаются редиректом 303 с одноразовым flash-сообщением в cookie.
  • Маршруты не фильтруют поля кандидатов самостоятельно: разграничение по тиру всегда проходит через helpers.candidate_card() → logic.candidate_visible_profile().
  • Проверка прав — guard-функции auth.py: при отсутствии доступа бросается RedirectException, её перехватывает общий обработчик в main.py.
  • Шаблоны обращаются к словарям как к элементам (row['match']), а не как к атрибутам (row.match), чтобы не попадать на dict.items(); глобальная функция tier_label продублирована алиасом tier_title, потому что маршруты работодателя кладут в контекст одноимённую строку.

5.1. Специализация кандидата (раздел 6.1)

Приоритет источников: 1) КИТ-сертификат → 2) дисциплина ФСП → 3) стек → 4) ручной выбор. Автоопределение не перезаписывает значение, если кандидат выбрал специализацию вручную (specialization_manual = True).

  • КИТ: текст специальности из сертификата сопоставляется со словарём KIT_SPECIALTY_KEYWORDS (например, «технической поддержки» → support, «данным»/«машинн» → ds, «фронт»/«веб» → frontend, «разработ»/«python» → backend).
  • ФСП: дисциплины достижений сопоставляются с FSP_DISCIPLINE_KEYWORDS («алгоритм» → backend, «беспилот»/«робот» → embedded, «данн»/«ml»/«ai» → ds, «продуктов» → backend).
  • Стек: STACK_SPEC_KEYWORDS; порядок словаря задаёт приоритет при равенстве числа совпадений.

Специальность берётся из распознанного поля сертификата (logic.kit_specialty_text → kit_parser.parse_kit_text), а не из всего текста документа: в шапке любого сертификата есть строка «Прошел(а) тестирование по специальности …» (п. 8.1 ТЗ), поэтому поиск ключевых слов по всему kit_raw срабатывал на слове «тестирование» и уводил любую анкету в QA. Регрессию проверяет tests/test_kit_specialization.py.

Коды специализаций: backend, frontend, ds, devops, qa, support, security, mobile, embedded, other (словарь SPECIALIZATIONS).

5.7. Релевантность пары «кандидат ↔ потребность» (разделы 6.6 и 10.3)

Функция logic.score_match() возвращает процент 0–100, краткую сводку и список причин. Веса (MATCH_WEIGHTS, сумма = 100):

ПризнакВесКак начисляются баллы
Специализация3535 — если специализация кандидата совпадает со специализацией потребности; 0 — если нет (совпадение проверяет specialization_match).
Стек25round(25 × matched / total) — доля совпавших элементов стека потребности. Если стек в потребности не указан: ≥ 3 элементов у кандидата → 25, 1–2 элемента → 12 (25 // 2), пусто → 0.
Грейд2020 — грейд не задан в потребности или режим any; 20 — грейд подходит по режиму (exact / plus_minus); 10 (20 // 2) — грейд соседний при plus_minus; 0 — не совпадает.
Верификация грейда1010 — грейд подтверждён сертификатом КИТ; 3 (10 // 3) — грейд заявлен кандидатом самостоятельно.
История ФСП10По категории: S → 10, A → 9, B → 7, C → 5, D → 2 (MATCH_FSP_POINTS); +1 балл за вердикт «амбициозный профиль», но не больше 10.
 
score = spec_points + stack_points + grade_points + verified_points + fsp_points
score = max(0, min(100, score))          # отсечение до диапазона 0…100

К каждому начислению формируется текстовая причина, например: «специализация совпадает: Backend-разработка», «стек: совпало 3 из 5 (python, fastapi, docker)», «грейд соседний: у кандидата Middle, в потребности Senior (указанный грейд ± 1 уровень)», «история ФСП: 120 баллов, категория A, амбициозный профиль».

Порядок подборки (rank_candidates)

  1. Отсев: профиль неполный → исключён; кандидат скрыл профиль → исключён; tier работодателя ниже минимального тира кандидата → исключён; специализация не совпадает со специализацией потребности → исключён.
  2. Сортировка по убыванию релевантности.
  3. При равной релевантности — строгий порядок раздела 6.6 (rank_key): верифицированный грейд выше неверифицированного → баллы КИТ по убыванию → баллы ФСП по убыванию → роль ФСП капитан/архитектор выше прочих → амбициозный профиль выше.

Дашборд работодателя сортирует отклики так: сначала новые (is_new), затем по убыванию релевантности.

Демонстрационная прозрачность

Веса, формула и поштучные причины сейчас показываются работодателю прямо в интерфейсе (страница потребности, карточка соответствия). В продукте эта методика закрывается — подробнее в главе 10, пп. 1–2.

9. Пользовательские сценарии

9.1. Кандидат: от входа до принятого приглашения

  1. Вход. /login?role=candidate → email → код из «письма» (в демо — на экране) → /verify.
  2. Шаг 1 — профиль и барометр. ФИО, город, специализация, стек, желаемая роль, формат работы, согласие на обработку данных. Система сразу считает флаги барометра и предварительный грейд.
  3. Шаг 2 — история ФСП. Подключение реестра: показываются достижения, сумма баллов, категория S–D и старшая роль. Можно пропустить — тогда fsp_score = 0, категория D.
  4. Шаг 3 — сертификат КИТ. Загрузка PDF/TXT: грейд, баллы, специальность, номер и дата. Грейд из сертификата перезаписывает предварительный и даёт метку «верифицирован». Можно пропустить и загрузить позже в кабинете.
  5. Кабинет. Кандидат видит: итоговый грейд и его источник, вердикт барометра, баллы и категорию ФСП, данные сертификата, строку матрицы видимости («топ ФСП», «опытный специалист», «новичок с амбициями» …), предупреждения по профилю, входящие приглашения. Здесь же — переключатель видимости в банке, редактирование анкеты, замена/удаление сертификата.
  6. Банк потребностей. /needs — список открытых вакансий с обязательной вилкой; /needs/{id} — описание, рейтинг компании словами и цифрой, предупреждения о сомнительных формулировках, форма отклика.
  7. Отклик. Сообщение → статус sent; работодатель переводит его в viewed / accepted / rejected.
  8. Приглашение. Кандидат видит сообщение, вилку, уровень процессов компании словами и её рейтинг. Принять → работодатель получает ФИО и email; отклонить → контакты не раскрываются.

9.2. Работодатель: от анкеты до раскрытия контактов

  1. Вход. /login?role=employer → email → код.
  2. Шаг 1 — профиль компании. Название, город, контактное лицо, должность, описание, согласие.
  3. Шаг 2 — анкета процессов. Шесть нейтральных вопросов; ответы сохраняются в JSON, из них считается тир. В демо-сборке уровень показывается словами сразу после сохранения (в продукте — нет, см. главу 10, п. 5).
  4. Потребность. /employer/vacancies/new: специализация, грейд и режим сопоставления (строго / ±1 / не важен), стек, вилка (обязательна), формат, город, размер команды, описание.
  5. Подборка. Страница потребности показывает ранжированный список: сначала фильтр по матрице видимости и полноте профиля, затем отбор по специализации, затем сортировка по релевантности и правилам раздела 6.6. Отдельно — число и замаскированные имена закрытых профилей.
  6. Банк кандидатов. /employer/bank с фильтром по специализации; карточки анонимны: маскированное имя, специализация, грейд, метка верификации, баллы КИТ, стек, достижения ФСП; для тира 2 добавляются амбициозность и роль ФСП, для тира 3 — город и полный профиль.
  7. Приглашение. Сообщение + вилка → sent. Статусы видны в /employer/invitations.
  8. Отклики. /employer/applications: новые сверху, далее по убыванию релевантности; смена статуса одним действием.
  9. Раскрытие контактов. Только после accepted со стороны кандидата работодатель видит ФИО и email — до этого в карточке маскированное имя, а в приглашении соответствующая сноска.
Сквозной демо-сценарий для защиты проекта

1) Зарегистрировать кандидата из мок-реестра ФСП (топ-уровень) и загрузить демо-сертификат КИТ → профиль становится «топ ФСП». 2) Зарегистрировать двух работодателей: с 6 «здоровыми» ответами (тир 3) и с 2 (тир 1). 3) Создать потребность у второго → топ-кандидат попадёт в закрытые профили, у первого → окажется на верхней строке подборки. 4) Отправить приглашение, принять его кандидатом → контакты раскрываются только у работодателя тира 3, пригласившего кандидата.

10.6. Почему это закрывается: пять причин

  1. Коммерческая тайна и защита от гейминга. Веса, пороги и коэффициенты — ядро продукта. Как только формула публична, пользователи оптимизируют анкеты под неё, а не отражают реальность: подборка теряет ценность.
  2. Персональные данные (152-ФЗ). ФИО, email, город, достижения и распознанный текст сертификата — ПДн. Демонстрационные механизмы (код на экране, демо-учётки, файл БД в репозитории, сырой текст распознавания) в продукте недопустимы: нужны минимизация данных, защищённое хранение, реестр согласий и право на удаление.
  3. Юридические и репутационные риски. Сообщения вида «уровень профиля выше, чем доступен при текущем уровне организации процессов» и публичный рейтинг с «разрывом зарплат» — оценочные суждения о компании и о кандидате. Без верифицированных источников и закрытой методики это повод для претензий и судов.
  4. Требование ТЗ. Раздел 5.2 прямо запрещает показывать работодателю его тир — ни цифрой, ни словами; категории ФСП и рейтинг предназначены только кандидату. Демонстрационная сборка эти границы намеренно раздвигает, и это надо закрывать до продуктивного релиза.
  5. Безопасность. Открытый Swagger, показ кода подтверждения, отсутствие rate limit и модерации — демонстрационные удобства, которые в продукте становятся векторами атаки и спама.
Что сознательно остаётся открытым и в продукте

Прозрачность правил для пользователя сохраняется там, где она полезна и безопасна: обязательная вилка зарплаты; факт верификации грейда сертификатом КИТ; состав открытых полей карточки; словесный уровень процессов компании в приглашении кандидата; статусы приглашений и откликов; правило раскрытия контактов только после принятия приглашения; возможность скрыть свой профиль из банка; объяснение релевантности в человеческих формулировках — но без весов, порогов и коэффициентов.

11.2. Ограничения MVP

  • Нет уведомлений (email, пуш): о приглашении и отклике пользователь узнаёт только в кабинете; счётчик «новых» считается по last_visit_at.
  • Нет чата и вложений: коммуникация — одно сообщение в приглашении/отклике.
  • Нет поиска по банку кроме фильтра по специализации; нет пагинации — записи выбираются в память целиком (list_candidates и др.).
  • Нет модерации текстов, жалоб, блокировок пользователей.
  • Нет логирования, метрик, экспорта данных, интернационализации.
  • SQLite в одном файле с check_same_thread=False: приемлемо для сотен записей, не рассчитано на высокую параллельную нагрузку.
